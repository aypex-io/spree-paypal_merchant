# Spree 6 Port Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Port `spree-paypal_merchant` to Spree 6.0.0 and release it as 6.0.0, with checkout, refunds and cancellations working through Spree 6's settlement, refund and webhook paths.

**Architecture:**
- **Settlement:** the gem stops creating payments itself. It implements Spree 6's settlement hooks on its `PaymentSession` subclass (`prepare_for_settlement!`, `payment_source_for_settlement`, `apply_settlement_metadata`). Both the storefront confirm call and the webhook settle through core's `settle_payment!`.
- **Gateway:** it keys payments on the PayPal order ID, reads the capture status to decide the outcome, and refunds through `Spree.refund_create_workflow`.
- **Removed:** the legacy pre-session flow and the Rails admin views.

**Tech Stack:** Ruby ≥ 3.3, Spree 6.0 (`spree ~> 6.0`), `paypal-server-sdk ~> 2.3`, RSpec with `spree_dev_tools >= 1.0.0.beta2`, PostgreSQL.

**Spec:** `docs/superpowers/specs/2026-10-28-spree-6-port-design.md` (read it with this plan; section and decision numbers below refer to it).

## Global Constraints

- Gemspec: `spree ~> 6.0`, `paypal-server-sdk ~> 2.3`, `required_ruby_version >= 3.3`; no `spree_admin` anywhere (gemspec, Gemfile, spec helper).
- Version `6.0.0`.
- Public repo: all code, comments, commits and PR text generic; commits authored `Matthew Kennedy <m.kennedy@me.com>`.
- Zero deprecation warnings: Spree's test setup raises `ActiveSupport::DeprecationException` on them. Use `customer` (not `user`), `delivery_total` (not `ship_total`), `discount_total` (not `promo_total`), `postal_code`/`country_code`/`state_code` (not `zipcode`/`country.iso`/`state.abbr`), `metadata` (not `private_metadata`), and never `cart.number`.
- Never call PayPal inside `owner.with_lock` / `settle_payment!`; provider I/O only in `prepare_for_settlement!` or before settling.
- A session's payment is linked by `Spree::Payment#response_code == PaymentSession#external_id` (the PayPal order ID). The capture ID lives in `payment.metadata['paypal_capture_id']`.
- The storefront contract is unchanged: session `external_data` keys `id`, `status`, `client_token`, `enable_apple_pay`, `enable_card_fields`; the Store API type is `paypal_merchant`; `public_preferences` stays on the payment method serializer.
- Tests stub `PaypalServerSdk` with doubles plus the JSON fixtures in `spec/fixtures/` (the existing pattern). No live PayPal calls.

## Review Focus

These failure modes are implied by the design but not obviously covered by its test list. Each has a test added to the task named.

1. **Guest checkout** (cart with no customer): the session is created, a source is built, no gateway customer is created, nothing raises. *Task 5 and Task 7.*
2. **An Apple Pay or Card Fields capture** settling, not only a PayPal wallet one: the right source class is attached. *Task 4.*
3. **A webhook for an unknown PayPal order ID or another gateway's session** returns nil and touches nothing. *Task 6.*
4. **A partial refund amount**, e.g. £12.50 of £75, is sent to PayPal as `"12.50"` against the right capture. *Task 7.*
5. **A partial charge** (store credit covers part) with fees or four-decimal prices sends only the charge amount, formatted to the currency's decimals, with no items or breakdown. *Task 8.*
